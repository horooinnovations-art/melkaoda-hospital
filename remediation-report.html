Four defects the source code could not show

Reading deployed_env_file/ changed the picture. The most serious one is a single variable.

MEL-DEPLOY-001 Critical The production API runs with NODE_ENV=development, disabling every production guard at once New
deployed_env_file/melkaoda.env APP_ENV=production ← says production NODE_ENV=development ← but the code reads THIS

isProduction() tests NODE_ENV and nothing else. With it set to development, the live API was running with:

  • No boot validation. The JWT secret, database password, admin password and Cloudinary credential checks are all gated on prod. None of them ran.
  • Error masking off. The old global handler returned err.message and the stack to the caller whenever isProduction() was false; /health echoed raw driver text naming the database host and schema.
  • The Cloudinary requirement bypassed, so a media upload could silently fall back to Render's ephemeral disk and vanish on the next deploy.
  • The default-ADMIN_PASSWORD refusal bypassed in bootstrapSchema.
Fixed — the mismatch is now a boot failure
// backend/src/config/env.js if (!prod && (appEnv === 'production' || appEnv === 'prod')) { errors.push( 'APP_ENV=production but NODE_ENV is not "production". Set NODE_ENV=production so the ' + 'production guards, error masking and Cloudinary requirement actually apply.' ); } $ node --test tests/envHardening.test.js ok 7 - APP_ENV=production with NODE_ENV=development is rejected

Error masking and the /health disclosure were additionally made unconditional, so a mis-set NODE_ENV can no longer turn disclosure back on even if this check is bypassed.

Your action

Set NODE_ENV=production on the melkaoda-hospital-api service. The API will refuse to boot until you do — that is deliberate.

MEL-SEC-017 High A plaintext Google account password sits in the API environment, for a mailer that does not exist New

So the credential is exposed for zero functional benefit. Anyone with Render dashboard access, or any log or error report that dumps the environment, gets a working Google login.

The same block also carries APP_KEY, SESSION_*, CACHE_STORE, QUEUE_CONNECTION and MIGRATE_FRESH — Laravel settings from the original CMS that this Express app also never reads. The corrected env file lists all of them for deletion.

MEL-BUG-002 High The migration runner silently discarded every migration, then recorded them as applied Fixed

Found while adding a migration for the new columns. The runner split each file on ; then dropped any chunk beginning with --. Since every migration in this project opens with a comment header, the first chunk always started with a comment — so it was discarded, and the file was still inserted into schema_migrations as done.

$ node -e "const sql=fs.readFileSync('database/migrations/002_doctor_department_category.sql','utf8'); console.log(sql.split(/;\s*\n/).map(s=>s.trim()).filter(s=>s && !s.startsWith('--')))" 002 statements the old runner would execute: [] 001 statements: 0 after the fix: 001_leadership_history.sql 1 statement(s) 002_doctor_department_category.sql 1 statement(s) 003_security_columns_and_partnerships.sql 3 statement(s)

Both existing migrations had therefore never run, while reporting success. The runner now strips comments per line instead of dropping statements, and refuses to mark a file applied if it parses to nothing — which is what hid the bug. Three regression tests cover it.

The two Criticals

How the access-control failures were closed

MEL-SEC-001 Critical Self-grantable super-admin tier → a non-user-editable database flag Fixed · 5 regression tests
- function hasAdminTerm(user) { - const email = String(user?.email || '').toLowerCase(); - const name = String(user?.name || '').toLowerCase(); - return email.includes('admin') || name.includes('admin'); - } + function isRootAdminFlag(user) { + const raw = user?.is_root_admin; + return raw === 1 || raw === true || raw === '1'; + }

The tier is now users.is_root_admin, a real column. Four things keep it out of reach of a request:

  • It is in sqlSafe.js's SYSTEM_COLUMNS, so getWritableColumns() subtracts it from every write path in the application.
  • updateMe, createUser and updateUser all build explicit column lists that do not include it.
  • It is granted only by ROOT_ADMIN_EMAILS at boot, or by direct SQL. Removing an address from that variable revokes the tier on the next deploy.
  • The SQL that hides root supers from lesser admins now keys on COALESCE(u.is_root_admin, 0) = 1 instead of LIKE '%admin%'.

The four 403 messages that used to name the bypass — “Only privileged Super Administrators (username containing ‘admin’)…” — now say only that permission is absent.

The regression test the original audit asked for
$ node --test tests/rbacPrivilege.test.js ok 1 - the old "admin" substring in name or email grants nothing ok 2 - editing one's own name or email cannot change the verdict ok 3 - the tier requires both the super_admin role and the root flag ok 4 - the root flag is read from the DB column in every shape MySQL returns it ok 5 - role slugs are accepted as strings or objects, but only exact matches # pass 5 # fail 0

Test 2 sweeps seven strings a PUT /admin/me body could carry — Admin, ADMIN, sysadmin, Chief Administrator, and one with an embedded zero-width space — and asserts the verdict is unchanged for every one.

MEL-SEC-002 Critical Boot-time admin resurrection → first-run provisioning only Fixed

ensureAdminAccount() ran on every API start and reversed administrator offboarding three ways. All three are gone:

- const syncPassword = process.env.ADMIN_SYNC_PASSWORD !== '0'; // default ON - // ...forced deleted_at = NULL, status = 'active' on every boot - UPDATE users u ... SET u.status = 'active' - WHERE r.slug IN ('super_admin','admin') AND u.status != 'active' ← no id filter - UPDATE users SET deleted_at = NULL WHERE id = :id ← first soft-deleted admin + // First run only: create an admin when the database has none at all. + if (!anyAdmin && !existing) { ...INSERT... ; return; } + // Every restore/reset path is behind ADMIN_RESET_PASSWORD, off by default. + if (breakGlass) { ...reset and reactivate, then warn to remove the flag... } + // Steady state: touch nothing. An operator who deactivated an admin meant it.

A deactivated or deleted administrator now stays that way across deploys and restarts. If the bootstrap account locks itself out, ADMIN_RESET_PASSWORD=1 for one boot recovers it and logs a reminder to remove the flag. Failures log at error, not warn.

Companion fix — MEL-SEC-004

The other half of this problem was in login(): it queried soft-deleted rows on purpose and cleared deleted_at on a correct password, so deleting a user revoked access only until they next signed in. The query now carries AND deleted_at IS NULL and the restore block is deleted.

Accepted risk

The shared database

MEL-ENV-001b High One users table serves four hospital deployments Accepted at your direction

You asked me to note this rather than plan or code around it, so it is recorded here as an accepted risk and excluded from the remediation work. It is not excluded from the score.

I found it by accident: after my changes, four accounts already held is_root_admin = 1, which my own code could not have produced. The column already existed — the Gambo project applied the same fix, and it shares this schema.

$ SELECT id, email, status, is_root_admin, roles FROM users WHERE deleted_at IS NULL # 1 ad***@ggh.com active root=1 super_admin # 2 ad***@ggh.com active root=0 admin # 3 mu***@gmail.com active root=0 admin # 5 ad***@dedrhospital.com active root=1 admin,super_admin # 6 ad***@gambohospital.com active root=1 admin,super_admin # 7 ed***@lokehospital.com active root=0 editor # 8 ab***@gmail.com active root=0 super_admin # 9 ha***@gmail.com active root=0 super_admin # 10 ad***@lokehospital.com active root=1 super_admin # 11 ab***@gmail.com active root=0 doctor schema: defaultdb tables: 52 domains: ggh.com, gambohospital.com, lokehospital.com, dedrhospital.com, gmail.com

What this means in practice: an administrator of the Gambo, Loke or Deder site can sign in to the Melka Oda admin panel with their existing credentials, and five of these accounts hold super_admin. Four hold the root tier, so they can also manage each other. Authentication and authorization here are correct — they are simply operating over a user list that is not only yours.

The MEL-SEC-001 fix is sound, but note the consequence: because the tier is a column in a shared table, its membership was set by another project's remediation. Setting ROOT_ADMIN_EMAILS on this service resolves that for this deployment, and will revoke the flag from the sibling accounts on the next boot — which may surprise whoever maintains those sites. Worth a message to them before you deploy.

If you decide to split it later
  1. Create a database for this deployment alone.
  2. mysqldump defaultdb, restore into it, then delete the user rows that belong to the sibling hospitals.
  3. Point DB_DATABASE at it, run npm run migrate, and keep SCHEMA_BOOTSTRAP=0.
  4. Give local development its own database as well — backend/.env currently points at the same remote instance the live site reads from.
